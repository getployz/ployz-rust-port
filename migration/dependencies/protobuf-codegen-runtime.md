## Scope and required behavior

This record covers generated **message** types, binary protobuf encoding and
decoding, well-known message types, `google.rpc.Status`, and descriptors. It
does not select or authorize a gRPC client/server generator, HTTP/2 transport,
executor, async runtime, cancellation model, or service framework. The service
declarations may remain present in file descriptors; no transport code is
generated by any eventually approved stack.

The input contract is the five immutable proto3 schemas:

- [`caddy.proto`](../../upstream/uncloud/internal/machine/api/pb/caddy.proto)
- [`cluster.proto`](../../upstream/uncloud/internal/machine/api/pb/cluster.proto)
- [`common.proto`](../../upstream/uncloud/internal/machine/api/pb/common.proto)
- [`docker.proto`](../../upstream/uncloud/internal/machine/api/pb/docker.proto)
- [`machine.proto`](../../upstream/uncloud/internal/machine/api/pb/machine.proto)

Together they require exact field numbers and wire types, proto3 implicit and
explicit presence/defaults, enums including unknown numeric values, multiple
oneofs, cross-file imports, `google.protobuf.Empty`, `Timestamp`, `Duration`,
and `Any`, plus `google.rpc.Status`. Proto3's specification requires unknown
fields to survive binary parse/serialize; see the official
[proto3 unknown-field rules](https://protobuf.dev/programming-guides/proto3/#unknown-fields)
and [field-presence rules](https://protobuf.dev/programming-guides/field_presence/).

### Oracle and caller observations

- All 615 schema lines, all 8,622 generated Go lines (including 1,803 gRPC
  lines), and both handwritten files were inspected. Generated headers identify
  `protoc` 5.27.3, `protoc-gen-go` 1.34.2, and `protoc-gen-go-grpc` 1.5.1; the
  frozen [`mise.toml`](../../upstream/uncloud/mise.toml) pins the corresponding
  generator command and the `internal/machine/api/vendor` import root.
- [`proxy/backend.go`](../../upstream/uncloud/internal/machine/api/proxy/backend.go)
  deliberately rewrites raw protobuf envelopes in `AppendInfo` and constructs
  `Metadata.status` in `BuildError`. Those paths depend on exact field numbers
  and protobuf concatenation rules but do not typed-decode and re-encode the
  payload, so the Rust port must preserve that raw-wire design.
- [`store/store.go`](../../upstream/uncloud/internal/machine/store/store.go) and
  [`corromigrate/migrate.go`](../../upstream/uncloud/internal/machine/corromigrate/migrate.go)
  use Go `protojson`; this decision does not silently select a protobuf JSON
  implementation. JSON behavior requires its own parity work if the package
  packet puts those callers in scope.
- No handwritten caller invokes `ProtoReflect` or a descriptor API; those calls
  occur only inside generated Go. Descriptors are nevertheless observable from
  the public generated API and are required for parity tests and future callers.
  [`common.go`](../../upstream/uncloud/internal/machine/api/pb/common.go) adds IP
  conversions and [`cluster.go`](../../upstream/uncloud/internal/machine/api/pb/cluster.go)
  adds network validation; neither is part of this message/codegen dependency
  choice.
- Go's v1.36.9 runtime stores ordinary unknown fields as raw wire bytes and
  appends them during marshal. The executable Go fixture preserved both an
  interleaved/non-minimal varint fixture and an unknown group byte-for-byte.
  rust-protobuf 3.7.2 stores four decoded unknown value kinds, normalizing their
  spelling/order, and explicitly **skips unknown groups**. The official warning
  that protobuf serialization is
  [not canonical](https://protobuf.dev/programming-guides/serialization-not-canonical/)
  means normalization by itself is not a hard failure; dropping a well-formed
  unknown field is. The proto3 guide says parsed unknown fields are included in
  serialized output, and the wire guide says deprecated groups remain in the
  wire format.

## Primary-source evidence

### Rejected stable runtime and generator

- The exact [`protobuf` 3.7.2 manifest](https://docs.rs/crate/protobuf/3.7.2/source/Cargo.toml.orig)
  declares MIT, edition 2021, no default features, and no async or native
  runtime dependency. It does not declare an MSRV. The Rust 1.96 probe below
  compiled the exact runtime and generated all requested schemas.
- [`Message`](https://docs.rs/protobuf/3.7.2/protobuf/trait.Message.html)
  exposes binary parse/write and explicit `unknown_fields` access. The exact
  [`UnknownFields` source](https://docs.rs/protobuf/3.7.2/src/protobuf/unknown.rs.html)
  says unknown fields are retained so messages can process and re-emit data
  added by newer schemas. Generated merge/write code calls
  `read_unknown_or_skip_group` and `write_unknown_fields`; however, the exact
  [`unknown_or_group.rs`](https://docs.rs/crate/protobuf/3.7.2/source/src/rt/unknown_or_group.rs)
  implementation stores varint, fixed32, fixed64, and length-delimited values
  but consumes and discards start/end groups. The generator source is visible in
  [`message.rs`](https://docs.rs/crate/protobuf-codegen/3.7.2/source/src/gen/message.rs).
- Unknown enum numbers remain values rather than becoming the enum default:
  [`EnumOrUnknown`](https://docs.rs/protobuf/3.7.2/protobuf/struct.EnumOrUnknown.html)
  stores the raw `i32`. The exact generator emits `EnumOrUnknown<E>` for enum
  fields and `Option<generated oneof enum>` for oneofs.
- Full-runtime generated messages implement
  [`MessageFull`](https://docs.rs/protobuf/3.7.2/protobuf/trait.MessageFull.html),
  whose `descriptor()` returns a message descriptor. The
  [reflection module](https://docs.rs/protobuf/3.7.2/protobuf/reflect/index.html)
  supports generated and dynamic messages and exposes file/message/field/enum/
  oneof/service descriptors. `lite_runtime(false)` is therefore mandatory.
- The exact [`protobuf-codegen` 3.7.2 documentation](https://docs.rs/protobuf-codegen/3.7.2/protobuf_codegen/)
  recommends `Codegen` from Cargo builds. Its own parser comparison says the
  `protoc` parser is more reliable and compatible with Google's compiler, while
  the pure-Rust parser is less tested and omits some complex options. The
  [`Codegen` API](https://docs.rs/protobuf-codegen/3.7.2/protobuf_codegen/struct.Codegen.html)
  accepts an explicit compiler path, ordered include roots and inputs, a Cargo
  output directory, and customization.
- `protobuf-codegen` maps imports of its recognized Google well-known types to
  the runtime's pregenerated modules rather than duplicating them. Its exact
  [well-known-type list](https://docs.rs/crate/protobuf-codegen/3.7.2/source/src/gen/well_known_types.rs)
  includes `Any`, `Duration`, `Empty`, and `Timestamp`; the rejected runtime's
  [well-known modules](https://docs.rs/protobuf/3.7.2/protobuf/well_known_types/index.html)
  retain unknown fields and full descriptors like ordinary generated messages.
- Generated files contain `_PROTOBUF_VERSION_CHECK =
  ::protobuf::VERSION_3_7_2`, preventing a silent generator/runtime version
  mismatch. Those are positive integration properties, but they do not repair
  the unknown-group behavior failure or lifecycle gate.

### Reproducible compiler and imports

- [`protoc-bin-vendored` 3.2.0](https://docs.rs/protoc-bin-vendored/3.2.0/protoc_bin_vendored/)
  returns both an exact compiler path and a bundled Google-proto include path.
  Its [`version.txt`](https://docs.rs/crate/protoc-bin-vendored/3.2.0/source/version.txt)
  identifies the bundled compiler as `protoc` v31.1. The include directory is
  documented and tested to be identical across packaged platforms.
- Its exact [manifest](https://docs.rs/crate/protoc-bin-vendored/3.2.0/source/Cargo.toml)
  pins binary packages for Linux x86, x86_64, aarch64, powerpc64le, and s390x;
  macOS x86_64 and aarch64; and Windows. Host-package selection uses build-host
  `std::env::consts`, so ordinary Cargo cross-compilation runs the host compiler
  while generating target-independent Rust. Unsupported build hosts fail
  explicitly rather than consulting `PATH` or downloading during `build.rs`.
- The wrapper is MIT. The bundled official protobuf source/binary is governed
  by Google's [protobuf v31.1 BSD-3-Clause license](https://github.com/protocolbuffers/protobuf/blob/v31.1/LICENSE).
  Exact pins and Cargo's checksum/lockfile protect the crate artifacts, but a
  precompiled build tool remains a supply-chain surface for the adversarial
  review.
- The frozen oracle already vendors the authoritative input
  [`google/rpc/status.proto`](../../upstream/uncloud/internal/machine/api/vendor/google/rpc/status.proto).
  Copy that file byte-for-byte, not a newer Google APIs revision. Its SHA-256
  at exact base `e86b2edc8d13c72e4ceaecc0b22a9ad778a0724f` is
  `b35706fa0e4b2354f67f8d7b8e6b55584d0c4dae920d5f6d2bc2e7ba22f9d6c1`.
  It carries an Apache-2.0 header and has exactly `int32 code = 1`, `string
  message = 2`, and repeated `google.protobuf.Any details = 3`. Vendor the
  Google APIs repository's
  [Apache-2.0 license](https://github.com/googleapis/googleapis/blob/ebd1d23ac613b177828dad42ad8dfb13ba498279/LICENSE),
  pinned at commit `ebd1d23ac613b177828dad42ad8dfb13ba498279`,
  SHA-256
  `c71d239df91726fc519c6eb72d318ec65820627232b2f796219e87dcf35d0ab4`,
  beside it for license provenance. The newer Status copy at that commit is
  not the schema input because source comments and source-info descriptors may
  be observable even when its wire declaration is unchanged.
- The official [well-known-type reference](https://protobuf.dev/reference/protobuf/google.protobuf/)
  defines `Empty`, `Timestamp`, `Duration`, and `Any`. In the rejected probe,
  the v31.1 compiler include root resolves their source imports and the Rust
  generator maps their message types to `protobuf::well_known_types`.

### Maintenance, adoption, and security snapshot

Official crates.io API values captured on 2026-08-11:

- [`protobuf`](https://crates.io/api/v1/crates/protobuf): 166,948,108 total /
  32,196,897 recent downloads and
  [567 reverse-dependent records](https://crates.io/api/v1/crates/protobuf/reverse_dependencies?page=1&per_page=1);
  stable 3.7.2 alone had 52,368,872 downloads.
- [`protobuf-codegen`](https://crates.io/api/v1/crates/protobuf-codegen):
  47,847,793 total / 9,206,950 recent downloads and
  [133 reverse-dependent records](https://crates.io/api/v1/crates/protobuf-codegen/reverse_dependencies?page=1&per_page=1);
  3.7.2 had 23,523,697 downloads.
- [`protoc-bin-vendored`](https://crates.io/api/v1/crates/protoc-bin-vendored):
  16,646,342 total / 7,778,767 recent downloads and
  [246 reverse-dependent records](https://crates.io/api/v1/crates/protoc-bin-vendored/reverse_dependencies?page=1&per_page=1);
  3.2.0 had 10,590,686 downloads.

Stable `protobuf`/`protobuf-codegen` 3.7.2 were released 2025-03-10;
`protoc-bin-vendored` 3.2.0 was released 2025-07-21. The stable runtime is mature
and materially adopted, but its current
[official README](https://github.com/stepancheg/rust-protobuf#end-of-life)
says this implementation is approaching end of life, version 3 remains the
current stable line, and a new maintainer is needed while Google's unrelated
implementation takes over the `protobuf = 4` name. This is the principal
maintenance risk and must not be hidden by the exact pin.

[`RUSTSEC-2024-0437`](https://rustsec.org/advisories/RUSTSEC-2024-0437.html)
describes uncontrolled recursion while parsing malicious unknown groups and
lists `>=3.7.2` as patched. The focused 58-package lockfile audit against the
locally current 1,211-advisory RustSec database reported no vulnerability. This
is a point-in-time result; the integrated lockfile still requires its normal
audit.

## No approved integration

The controller must not release a package from the dependency gate and the
integrator must not add any protobuf stack yet. For reproducibility, the exact
**rejected** 3.7.2 probe used these entries:

```toml
[dependencies]
protobuf = { version = "=3.7.2", default-features = false }

[build-dependencies]
protobuf-codegen = "=3.7.2"
protoc-bin-vendored = "=3.2.0"
```

`protobuf` has `default = []`; the probe kept `default-features = false` and did
not enable `with-bytes`. These are evidence coordinates, not authorization.

The leading Google-v4 probe used exact runtime dependencies
`protobuf = "=4.35.1-release"` and
`protobuf-well-known-types = "=4.35.1-release"`, plus exact build dependencies
`protobuf-codegen = "=4.35.1-release"` and
`protobuf-well-known-types = "=4.35.1-release"`. It has no relevant Cargo
feature choice: open-source builds use the upb kernel and compile bundled C via
`cc`. Approval additionally requires an exact protoc 35.1 host tool, not
`protoc-bin-vendored` 3.2.0.

Do not add any candidate or `prost-reflect`, `tonic`, `grpc`, Tokio, async-std,
smol, Hyper, or a transport generator under this blocked decision.

```text
│   ├── caddy.proto
│   ├── cluster.proto
│   ├── common.proto
│   ├── docker.proto
│   └── machine.proto
└── google/rpc/
    ├── LICENSE

```

The five Ployz copies and Status copy must compare byte-for-byte with the
frozen oracle. Vendor the Apache license with the pinned commit and hash above.
Do not copy Google WKT schemas into the project: an eventual approved candidate
must resolve those from its exact compiler/WKT package and use its pregenerated
WKT types. The first include root is the crate's `proto/`; the second is the
exact compiler include root. No ambient include directory is permitted.

### Required build configuration

The following is the exact rejected-3.7.2 probe configuration, retained solely
so the result can be reproduced. It is **not** an approved `build.rs`. Status is
an explicit sixth generator input; it is supporting schema, not a sixth
Ployz-owned wire contract.

```rust
let proto_root = std::path::PathBuf::from("proto");
let api_root = proto_root.join("internal/machine/api/pb");
let inputs = [
    api_root.join("caddy.proto"),
    api_root.join("cluster.proto"),
    api_root.join("common.proto"),
    api_root.join("docker.proto"),
    api_root.join("machine.proto"),
    proto_root.join("google/rpc/status.proto"),
];

for input in &inputs {
    println!("cargo:rerun-if-changed={}", input.display());
}

let compiler = protoc_bin_vendored::protoc_bin_path()
    .expect("supported build host for vendored protoc");
let google_includes = protoc_bin_vendored::include_path()
    .expect("vendored protobuf include root");

protobuf_codegen::Codegen::new()
    .protoc()
    .protoc_path(&compiler)
    .includes([proto_root, google_includes])
    .inputs(inputs)
    .cargo_out_dir("generated")
    .customize(
        protobuf_codegen::Customize::default()
            .lite_runtime(false)
            .gen_mod_rs(true),
    )
    .run_from_script();
```

The probe included only `concat!(env!("OUT_DIR"), "/generated/mod.rs")`, never
wrote to `src/`, never fell back to `PATH`, and never switched to `.pure()`.
Any future approved strategy must preserve those reproducibility properties.

- Use the eventually selected dependency's natural message, presence, enum,
  oneof, WKT, and reflection APIs. Do not wrap it to imitate Go's `protoimpl` or
  generated getter names. The API names above describe only the rejected v3

- `Any` is wire data (`type_url`, `value`); do not add JSON mapping or network
  type-resolution behavior under this decision.
- Descriptor golden tests must assert fully

## Known limitations and risks

- rust-protobuf 3.7.2 is explicitly approaching end of life and needs a
  maintainer. Its current adoption and patched release do not remove that
  lifecycle failure.
- rust-protobuf stores only four decoded unknown value kinds. It normalizes
  unusual ordering/non-minimal varints and discards unknown groups. Google v4's
  upb kernel preserved all tested raw bytes, including a group, but its stable
  Rust reflection surface is not present in 4.35.1-release.
- `protoc-bin-vendored` downloads packages for every supported platform, not
  only the current host. This increases registry/cache and supply-chain weight.
  Unsupported build hosts fail; there is deliberately no system fallback.
- The vendored compiler is a native executable run at build time. Cargo crate
  checksums cover distribution, but this is not equivalent to compiling the
  compiler from audited source.
- The rejected 3.7.2 crates do not declare an MSRV. Rust 1.96 compatibility is
  probe evidence, not a future-version guarantee; exact pins are mandatory.
- Generated Rust is verbose and deliberately carries broad lint allowances.
  Review schemas, generator configuration, descriptor goldens, and deterministic
  output hashes; do not hand-edit generated output.
- The 3.7.2 runtime has internal unsafe code but no FFI/native library in its
  runtime path. Google v4 compiles and links bundled C upb and therefore adds a
  native/FFI target-toolchain surface. Continue fuzzing and size/depth limits
  at the eventual transport boundary; this decision does not define request
  size policy.
- Neither evaluated probe emitted a gRPC client/server implementation. Any
  attempt to add tonic, grpc, HTTP/2, TLS, futures, or an executor must wait for
  the separate async gRPC transport/codegen dependency decision.
